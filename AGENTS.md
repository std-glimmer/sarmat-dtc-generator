# AGENTS.md — SarmatDTC (sarmat-dtc-generator)

Мод для DCS World: при подключении к мультиплеерному серверу, в названии которого есть **SARMAT**,
скачивает обстановку с живой карты <https://baikalprimestudio.com/map.html> и при выборе слота
генерирует картриджи DTC для AH-64D, F-16C, F/A-18C и F-14BU.

## Где лежит репозиторий

Корень репозитория — папка `%USERPROFILE%\Saved Games\DCS.openbeta`. В ней много чужих файлов
(конфиги, логи, ливреи, другие моды). `.gitignore` работает как **allowlist**: в git попадает только
то, что явно разрешено. Новый файл мода нужно добавить в `.gitignore` через `!`, иначе git его не увидит.
Ничего вне перечисленных ниже путей не трогать и не коммитить.

| Путь | Назначение |
|---|---|
| `Scripts/Hooks/SarmatDTC-hook.lua` | Загрузчик: DCS исполняет все файлы из `Scripts/Hooks` в GUI-окружении |
| `Scripts/SarmatDTC/config.lua` | **Пользовательские настройки**: `AIRCRAFT` — для каких самолётов генерировать (ненужные закомментировать), `BASE_DTC[type]` — базовый DCS-картридж, из которого берутся все незаполненные поля, `OPTIONS[type]` — опции модулей и их выходов. Перечитывается при каждом старте миссии |
| `Scripts/SarmatDTC/SarmatDTC.lua` | Связь с DCS: колбэки, определение сервера и стороны, загрузка, поиск модулей, кодировщики форматов и запись файлов. Технический `CONFIG` в начале файла |
| `Scripts/SarmatDTC/SarmatDTC_core.lua` | Общая библиотека без зависимостей от DCS: данные карты → нейтральная «обстановка» (`situation`), классификация юнитов и ПВО, геометрия, загрузка и запуск модулей |
| `Scripts/SarmatDTC/aircraft/<type>.lua` | **Один файл на модуль DCS**: переводит обстановку в DTC этого модуля, держит его символы и лимиты. Подхватывается автоматически |
| `Scripts/SarmatDTC/aircraft/_template.lua` | Шаблон модуля с описанием API (файлы на `_` не загружаются) |
| `Scripts/SarmatDTC/fetch.vbs` | Запускает `fetch.cmd` в скрытом окне и сразу возвращает управление |
| `Scripts/SarmatDTC/fetch.cmd` | `curl.exe` → `cache/status.json`, `cache/units.json`, затем `cache/done-<id>.flag` (`ok`/`fail`) |
| `Scripts/SarmatDTC/tests/` | Офлайн-тесты и фикстуры (снимок данных карты, Сирия) |
| `Scripts/SarmatDTC/cache/` | Кэш загрузки, генерируется во время работы, в git не попадает |

Результат: `DTC/SARMAT_<type>.dtc` для каждого самолёта из `config.lua` (`AIRCRAFT`), у которого
есть модуль в `aircraft/` (сейчас `AH-64D_BLK_II`, `F-14BU`, `F-16C_50`, `FA-18C_hornet`), плюс файлы
дополнительных выходов модулей (`outputs`). Каждый файл существует в одном экземпляре
и перезаписывается при каждом выборе слота.

## Архитектура модулей

```
status.json + units.json ──core.situation()──► situation ──► aircraft/<type>.lua ──► outputs ──► ENCODERS ──► файлы
                                                              build   → "dcs-dtc" (DTC\SARMAT_<type>.dtc)
                                                              outputs → любые другие форматы/папки
```

- **API модуля** (поля, `situation`, `lib`, `outputs`, варианты, `limits`) описан только
  в `aircraft/_template.lua`: это единственный полный справочник, тест проверяет, что шаблон
  остаётся рабочим модулем. Здесь — только устройство и решения.
- `situation` не знает про конкретные самолёты. Модуль возвращает `{ type, options, limits?, base?,
  build?, outputs?, variant?, variants? }`: `build` — нативный картридж DCS (выход `dcs-dtc`, всегда
  первый, строится даже при отключённой записи), `outputs` — файлы для **других DTC-систем**,
  которые получают `built["dcs-dtc"]`.
- **Лимиты опций** (`limits = { NAME = { min, max, int = true } }`): `core.build` после слияния опций
  округляет и прижимает значения из `config.lua` к границам, а не-число заменяет значением
  по умолчанию модуля или варианта. Предупреждение (`config.lua option: F-16C_50: POINTS = 30 is out
  of range, using 25`) пишется в `dcs.log`, но не считается ошибкой в чате. Тест требует `limits`
  у каждой числовой опции модуля и проверяет, что значения по умолчанию в них укладываются.
- Форматы (кодировщики `ENCODERS` в `SarmatDTC.lua`): `dcs-dtc` (обёртка `{data, name, type}` + JSON
  в стиле DCS), `json`, `lua` (`return {...}`), `text` (строка как есть). Новый формат — новая функция
  в `ENCODERS`.
- `dir`: путь относительно `Saved Games\DCS.openbeta`, абсолютный (`C:\...`, `\\server\...`) или
  с `%ENV%`; в `dir`/`file` работают `{type}`, `{side}`, `{terrain}`. Папки создаются автоматически.
- `core.build` мёржит `options` модуля с `config.lua OPTIONS[type]` (`enabled = false` отключает модуль,
  `outputs[id] = { enabled, dir, file }` — переопределяет выход) и вызывает каждый модуль и выход
  через `pcall`: сбой одного не мешает остальным (в лог `cartridge failed: <type>/<id>: ...`).
- Дополнительный выход может вернуть `nil` — «писать нечего»: он попадает в результат как
  `{ skip = true, stats }`, а в логе отображается как `<type>/<id> not written (...)`. Так устроен
  пример `aircraft/F-15ESE.lua`: у F-15E нет нативного DTC в DCS, а целевой формат ещё не выбран.
  Build его выхода собирает всё доступное в таблицу `d` (спавн, фронт, угрозы, цели, свои,
  FARP-ы; у каждой точки x/z, lat/lon, высота в м и ft) и возвращает `nil, stats`. В шапке файла
  описано, во что эти данные можно превратить, а в конце build лежит закомментированный пример
  итоговой генерации. Тест проверяет, что этот пример компилируется. Чтобы довести модуль
  до конца, нужно заменить `return nil, stats` на возврат данных целевого формата.
- **Варианты** (альтернативные алгоритмы заполнения, выбор — `config.lua OPTIONS[type].variant`):
  опции сливаются как `mod.options` → `variants[v].options` → `OPTIONS[type]` (ручные настройки
  главнее пресета). Неизвестное имя — ошибка в лог и вариант по умолчанию. В логе тип пишется
  как `AH-64D_BLK_II[sortie]`, в чате вариант виден, только если он не по умолчанию. Пишется один
  вариант на самолёт. У AH-64 сейчас один вариант `sortie` (текущий алгоритм).
- Загрузчик (`moduleProblem` в ядре) отклоняет неверный модуль и пишет в лог конкретную причину:
  нет `type`, нет ни `build`, ни `outputs`, у выхода нет `id`/`file`/`build`, `id` повторяется
  (`dcs-dtc` зарезервирован), неверные `variants` или `limits`.
- Префикс имени нативного файла (`CONFIG.FILE_PREFIX`) передаётся в `core.build` параметром,
  поля ядра снаружи не меняются.
- `config.lua AIRCRAFT` задаёт и набор, и порядок генерации (`core.selectModules`); тип без модуля
  даёт предупреждение в лог. Если `config.lua` не читается, генерируются все модули.
- Классификация (`AD_TYPES`, `GROUND_CLASSES`) общая, она живёт в ядре и выдаёт **ключи**
  (`"SA-11"`, `"armor"`). Символы конкретного модуля (ID Apache и т.п.) — только в его файле.

## Поток работы

1. `onMissionLoadEnd`: `DCS.isMultiplayer()` и `net.get_server_settings().name` содержит `sarmat`
   (без учёта регистра) → `state.active`. Карта местности берётся из `Terrain.GetTerrainConfig('id')`.
   Сирия → `/data/`, Кавказ → `/k/data/`. Запускается фоновая загрузка.
2. `onSimulationFrame`: раз в секунду проверяется `cache/done-<id>.flag` своей загрузки. У каждой загрузки
   свой id (`os.time()-<счётчик>`): `fetch.vbs` передаёт его в `fetch.cmd`, тот пишет `status-<id>.part`
   и флаг с этим id. Поэтому поздно завершившийся старый процесс (например, после перезахода) не принимается
   за текущую загрузку. Перед новой загрузкой старые `done*.flag` удаляются. `FETCH_TIMEOUT` (240 с) должен быть
   больше худшего случая `fetch.cmd` (~200 с: попытка ≤ 40 с, повторы стартуют не позже 60 с, два файла).
3. `onPlayerChangeSlot(id)` для своего id: сторона (`1`=red, `2`=blue; `0`, то есть зритель, игнорируется).
   Если кэшу больше `REFETCH_SEC`, DTC сразу генерируется из старого кэша, затем идёт перезагрузка,
   и после неё DTC генерируется ещё раз.
4. Перед генерацией `status.theatre` сверяется с картой миссии: при несовпадении генерация пропускается.
5. Возраст кэша определяется по времени файла `cache/status.json`. Кэш старше `MAX_AGE_SEC` (3 ч) не используется,
   а для кэша старше `STALE_SEC` (10 мин) в чат добавляется `map data N min/h old`.
6. `generate(final, problem)`: `final = false` — попытка из старого кэша перед загрузкой, её отказ пишется
   только в лог. `final = true` — после загрузки (успешной, неудачной или по таймауту): если ничего не записано,
   игрок получает в чат причину (`..., no DTC written`), а `problem` (`download failed`/`download timed out`)
   добавляется к сообщению.
7. Запись файла (`writeFileAtomic`): `.tmp`, затем старый файл переносится в `.bak`, затем `.tmp` ставится на его место.
   Если замена не удалась (файл занят), старый возвращается: сбой записи не уничтожает прежний картридж.
8. **Без изменений — без перезаписи.** `inputKey` = сторона + база спавна + время файлов базовых DTC +
   текст `status`/`units`. Если ключ совпал с последней успешной записью и все записанные файлы на месте,
   генерация пропускается молча (в логе `map data unchanged, cartridges kept`): нет второго разбора JSON
   (~75 мс на GUI-потоке) и второй перезаписи файла. Решение владельца — в чат ничего не писать. Если
   загрузка не удалась (`problem`), пропуска нет: это новая информация для игрока. Неудачная запись
   ключ сбрасывает.
9. Все колбэки обёрнуты в `pcall` целиком (`safeCallbacks`): ошибка не доходит до GUI игры, а каждое
   уникальное сообщение пишется в лог один раз (иначе `onSimulationFrame` повторял бы его каждый кадр).

`generate` разбит на шаги: `loadCache` (текст и возраст) → `inputKey` → `decodeCache` (JSON, карта) →
`core.build` → `writeOutputs` → `report` (строка в лог и в чат).

## Данные сайта (публичный JSON, координаты уже в системе DCS)

- `data/status.json`: `front[] {x,z}` — линия фронта; `objectives[]` (`kind`: `FARP`/`FOB`/`Airfield`…,
  `owner`); `strong[]` (`kind: "SAM"`, `name` вида `"SAM SA-11 RED-1"`, `dead`; `alive=0` означает
  «спит/не заспавнен», а не «уничтожен»); `theatre`.
- `data/units.json`: `groups[] {cat, side, type, types[], count, x, z, name}`, где `cat` — `ground`/`ship`.
- DCS x/z → в DTC пишутся как `x` (север) / `y` (восток).
- Сайт работает только по HTTPS (HTTP отдаёт 308) и иногда таймаутит соединения. Не долбить его
  запросами при отладке: используйте фикстуры.

## Правила DTC (сверено с `CoreMods/aircraft/*/DTC/*.lua` в установке DCS)

- Файл — JSON `{"data": {...}, "name": "", "type": "<type>"}`. Импорт в DCS:
  `Scripts/UI/DTC_manager/DTC_manager_PanelCommon.lua` → `setData` модуля. Загрузчик **сбрасывает
  всё к умолчаниям и накладывает поля из файла**, поэтому пишем только разметку («чистые» шаблоны).
- AH-64D и F-16C импортируют навигацию, только если `terrain` совпадает с текущей картой.
- Лимиты — в `options` каждого модуля: AH-64 CTRLM 49 (номера 51–99, `text` ≤ 3 символов), TGT 50
  (используем 25, см. ниже), Lines 15×(2–4 вершины);
  F-16 GEO LINES 25 точек (31–55, линия L1, `mirror_GEO_LINES=false`); F/A-18 FLOT 3×7
  (`mirror_MEZ_THRTS=true` обязателен, иначе сбрасывается в nil); F-14 4×9, но не больше 20 точек на план,
  поэтому используем 2×9.
- Линии длиннее лимита: `M.simplify` (Дуглас–Пекер по числу точек) → `M.chain`
  (соседние линии делят конечную точку).
- ID символов AH-64 — `CoreMods/aircraft/AH-64D/DTC/NAV/Points.lua` (`PointsID`). Тип линии FLOT = `type_num 4`.

## Отбор точек AH-64 (`aircraft/AH-64D_BLK_II.lua`)

Картридж планируется как картинка TSD на один вылет, а не копия всей карты (сверено с
`Mods/aircraft/AH-64D/Doc/DCS AH-64D Flight Manual EN.pdf`, разделы Points и TSD COORD SHOW).

- Район действий (если база спавна известна): объекты не дальше `расстояние от базы до фронта +
  AO_DEPTH_M` (80 км) от базы; для угроз из расстояния вычитается кольцо (`RING_CAP_M`). Свои FARP —
  только не дальше от фронта, чем база (+5 км): тыловые FARP не по пути. `AO_DEPTH_M = 0` — вся карта.
- Один символ на позицию (`CLUSTER_M`, 2 км): группы одной стороны жадно, в порядке приоритета,
  сливаются с более важной группой (её позиция — это реальный юнит, а не центр масс; класс — по
  большинству машин, generic — только если других нет; машины суммируются). Свои и вражеские не
  сливаются. Группы рядом с FARP/FOB своей стороны входят в точку FARP (у вражеского FARP в заметке
  число защитников). `CLUSTER_M = 0` — без слияния.
- Свои войска — только в пределах `OWN_FRONT_M` (10 км) от фронта (риск огня по своим); свои ПВО
  не показываются (`OWN_AD = false`): для вертолёта они не угроза.
- Free text CTRLM на TSD показывается вместо номера точки, а пустой текст = номер (`C51`),
  поэтому для юнитов пишем число машин, для FARP — `F01…` (свои) / `E01…` (вражеские).
  Подробности — в `note` (видна на странице POINT). Порядок списка CTRLM: свои FARP, противник, свои.
- Приоритет CTRLM (`lib.byScore`, меньший вес побеждает): `вес = расстояние до фронта + SPAWN_WEIGHT ×
  расстояние до своей базы спавна`, у вражеских объектов вес × `ENEMY_FACTOR` (по умолчанию 0.5 и 0.7).
  Если база спавна неизвестна, остаются фронт и приоритет вражеских. `SPAWN_WEIGHT = 0` —
  игнорировать спавн, `ENEMY_FACTOR = 1` — без предпочтения.
  Опция `CTRLM_FARPS = nil` — общий список (решение владельца: оставить так, без квоты);
  `config.lua OPTIONS['AH-64D_BLK_II'] = { CTRLM_FARPS = N }` резервирует до N слотов под FARP-ы.
- TGT: только вражеские ПВО. Группа, где есть хоть один ПВО-юнит, считается ПВО; тип — самый
  опасный по порядку `AD_TYPES`. Плюс ЗРК-площадки из `strong`, не покрытые живой группой своей
  стороны в радиусе 2 км. Ключ ПВО → символ через `TGT_IDS` в модуле. Один тип ПВО в радиусе
  `CLUSTER_M` — одна точка. Вес: `расстояние до фронта − кольцо (core.THREAT_DEFS, не больше
  RING_CAP_M = 15 км, горизонт РЛС для низколетящего вертолёта) + SPAWN_WEIGHT × расстояние до базы`.
- `TGT = 25`: T01–T25 — «safe set» DTC, его не перезаписывают сохранения из кабины. Точки, которые
  экипаж сохраняет через TADS/HMD/NOW, попадают в первую свободную TGT, поэтому T26–T50 оставлены пустыми.

## Базовый картридж (`config.lua BASE_DTC`)

- `BASE_DTC[type]` — нативный DCS `.dtc` (имя в `Saved Games\DCS.openbeta\DTC` или абсолютный путь).
  `SarmatDTC.lua loadBases()` читает и кэширует его (по пути и `modification`), проверяет `type`
  и отклоняет собственный выходной `SARMAT_<type>.dtc`.
- `core.applyBase(base, ours, mod.base, terrain)` применяется только к нативному выходу `dcs-dtc`
  (дополнительные `outputs` получают уже объединённый `built["dcs-dtc"]`). Результат — копия базы,
  поверх которой наложены наши данные:
  скаляры и **непустые списки** из наших данных заменяют базовые (никаких хвостов старых точек),
  словари сливаются рекурсивно, **пустая таблица у нас сохраняет значение базы**, пути из
  `mod.base.byIndex` заменяются поэлементно (F-14 `NAV`: план 1 наш, 2–12 из базы).
- `mod.base.terrainPaths` — секции, привязанные к карте. Если `terrain` базы известен и отличается
  от текущего, они удаляются из базы до слияния (в логе: `base DTC is for another map, not used: ...`).
  F-14 не пишет `terrain`: его базовый файл используется как есть.
- Поэтому модуль не должен выдавать пустые «заглушки» для секций, которые он не заполняет
  (из AH-64 убран пустой `WPTHZ`); пустой список у нас — это «не заполнено».
- В логе генерации у типа с базой появляется пометка `+base`.

## Угрозы ЗРК для F-16 и F/A-18

- Общий отбор — `lib.enemyThreats(situation, limit, opt)`: вражеские ПВО-группы и ЗРК-площадки, без
  `RADAR` и без типов с радиусом меньше `MIN_RANGE` (по умолчанию 6 км: отсекает ЗУ, ПЗРК, SA-9/13,
  Avenger), не больше одного кольца одного типа в радиусе `DEDUP_M` (5 км). Порядок — по удалению
  края кольца от фронта (`расстояние до фронта − радиус`): сначала кольца, перекрывающие фронт.
- `core.THREAT_DEFS`: ключ ПВО → название из справочника ED, текст (≤ 3 символов), радиус и высота.
  Справочник у F-16 (`MPD/THREAT_PTS_defs.lua`) и F/A-18 (`SA/MEZ_THRTS_defs.lua`) один и тот же;
  тест сверяет названия с файлами установки DCS. Нет типа в ED — `"Custom"`.
- F-16 `MPD.THREAT_PTS` (до 15, номера 56–70): `threatName`, `def_num` (индекс в `THREAT_PTS_defs`,
  таблица `DEF_NUM` в модуле), `radius` [м], `alt`, `elev`, `text`, `ring = true`; `mirror_THREAT_PTS = false`.
- F/A-18 `SA.MEZ_THRTS` (до 40): `threat_type`, `threat_ring_radius` [**NM**], `threat_level` (1–3), `text`;
  `mirror_MEZ_THRTS = false` (иначе берутся угрозы миссии).
- Опция `THREATS = 0` возвращает угрозы из миссии (`mirror = true`).

## Ловушки окружения (проверено, не «упрощать» обратно)

- **`os.execute` в Lua от ED молча игнорирует команды длиннее ~256 символов**: не выполняет и ничего
  не возвращает. Команда запуска сделана короткой (VBS сам вычисляет папку кэша), а при длине больше 250
  в лог пишется предупреждение.
- `start "" file.cmd` хостит батник в `cmd /K`: окно остаётся висеть. Поэтому используется `wscript` + `Run(..., 0, False)`.
- `.cmd`/`.vbs` должны быть в CRLF (`.gitattributes`). Инструмент Write пишет LF: после правок проверять
  `file fetch.cmd`.
- В GUI-окружении нет HTTPS в Lua (только LuaSocket без SSL), поэтому используется системный `curl.exe`.
  Его флаги в `fetch.cmd` — защита от недоверенного ответа: `--proto =https,file` (`file` нужен только
  офлайн-тесту, базовый адрес зашит в коде), `--proto-redir =https` (без понижения до http),
  `--max-filesize 5M` (JSON разбирается на GUI-потоке, огромный ответ подвесил бы игру).
- `Scripts/JSON.lua` из DCS: старый JSON.lua Фридла; пустые таблицы кодирует как `[]`, загрузчикам DCS это не мешает.
- Lua 5.1: без `goto`, без `//`, `#` для массивов, в строке замены `gsub` знак `%` надо экранировать.

## Информация о слоте и база спавна

`net.get_player_info(myId, 'slot')` → id слота (unitId; у многоместных `unitId_seat`).
`DCS.getAvailableSlots('red'|'blue')` → `{unitId, type, role, callsign, groupName, country,
airdromeId?, helipadId?, takeOffType, multicrew_place}`.
`airdromeId` → `Terrain.GetTerrainConfig('Airdromes')[id]` (`display_name`/`names.en`, `reference_point.x/y`);
`helipadId` → `DCS.getFarpsAndCarriersMissionData().farps[id]` (или `.carriers`) → `name, x, y`.
Это то же, что использует экран выбора роли (`Scripts/UI/MultiplayerSelectRoleMap`). При `CONFIG.LOG_SLOT`
результат пишется в `dcs.log` строкой `own slot (...)`. Координаты базы при каждой смене слота
сохраняются в `state.spawn` и передаются модулям как `env.spawn` → `situation.spawn = {x, z, name}`
(в логе: `cartridges written for <side> around <base>`). На живом сервере SARMAT поля ещё
не проверялись, особенно для динамических слотов: если координат нет, `spawn = nil`.

## Скиллы

### 1. Запуск тестов (после любого изменения кода)
```powershell
powershell -ExecutionPolicy Bypass -File "Scripts\SarmatDTC\tests\run_tests.ps1"
# путь к DCS: -DcsDir, иначе переменная DCS_DIR, иначе реестр (HKCU\Software\Eagle Dynamics\DCS World*)
# сохранить сгенерированные DTC: -OutDir <папка>; записать новые эталоны: -UpdateExpected
```
- `test_core.lua`: поиск модулей; общие проверки **для каждого** модуля (`type`, `terrain`, `name`,
  JSON-сериализуемость, числовые `stats`); изоляция сломанного модуля и `enabled = false`; затем
  проверки лимитов и сцепки линий для известных модулей (обе стороны, с квотой FARP и без).
  Варианты: синтетический модуль (пресет, свой `build`, приоритет config, неизвестное имя),
  сборка **каждого** варианта каждого модуля, отказ загрузчика на неверных `variants`.
  `limits` опций (прижатие, не-число, значения по умолчанию в пределах), шаблон как рабочий модуль.
- **Эталоны** `tests/fixtures/expected/*.lua`: все модули с опциями по умолчанию, обе стороны,
  со спавном и без, сериализованы `core.toLua` и сравниваются побайтно. Рефакторинг должен
  сохранять их. Если вывод меняется намеренно, запустить `run_tests.ps1 -UpdateExpected`
  и посмотреть дифф эталонов в git (`-text` в `.gitattributes`, чтобы CRLF не ломал сравнение).
- `test_hook.lua`: `SarmatDTC.lua` с заглушками `DCS`/`net`/`log`/`lfs`/`terrain` и **реальной** загрузкой
  через `wscript → fetch.cmd → curl` по `file://`. Временная папка лежит в коротком `%TEMP%\sdtc*`
  из-за лимита в 256 символов. Тест подкладывает свой `config.lua` (F-14 закомментирован, есть
  неизвестный тип) и модуль `ZZ_TEST` только с `outputs` (text/lua/json; относительный, абсолютный
  и `%TEMP%` пути) и проверяет реально записанные файлы. Режим загрузки переключается (`download`:
  `ok`/`fail`/`none`), время файла кэша подменяется (`mtime`). Проверяются чужие флаги, возраст кэша в чате,
  слишком старый кэш, кэш другой карты, таймаут, пропуск неизменных данных (и повторная запись
  удалённого картриджа), ошибка в колбэке и отсутствие `.tmp`/`.bak` рядом с картриджами.
- Интерпретатор — `bin\luae.exe` из установки DCS (Lua 5.1), запускать с рабочей папкой в корне DCS.
- В DCS реально не запускается: после изменений в колбэках просить пользователя проверить в игре
  (`Logs\dcs.log`, тег `SARMAT.DTC`).

### 2. Добавить новый модуль (самолёт/вертолёт)
1. Найти `CoreMods/aircraft/<module>/DTC/` (или `Mods/aircraft/...`) в установке DCS (только чтение).
2. В `<type>_DTC.lua` прочитать `data` (поле `type`!) и `setData`: какие ключи импортируются,
   есть ли проверка `terrain`, какие `mirror_*` нужно задать явно.
3. Найти лимиты (`MAX_*`) и структуру точек/линий в файле нужной секции.
4. Образцы реальных файлов — в `DTC/` пользователя (сохранены редактором DCS).
5. Скопировать `aircraft/_template.lua` в `aircraft/<type>.lua`, заполнить `type`, `options`,
   `limits` (границы из `MAX_*` для каждой числовой опции) и `build`, затем добавить тип в `AIRCRAFT` в `config.lua` (тест проверяет, что поставляемый
   `config.lua` перечисляет все модули). Ни ядро, ни `SarmatDTC.lua` трогать не нужно.
6. Если в `situation` не хватает данных (например, аэродромов), добавить их в `M.situation`
   нейтрально (ключи, а не символы модуля) и описать в `_template.lua`.
7. Добавить специфичные проверки в `test_core.lua` (общие проверки уже покрывают новый модуль)
   и запустить тесты.

### 2a. Добавить выгрузку для другой DTC-системы (не нативный DCS)
1. Выяснить формат и место хранения файлов этой системы (по документации или по реальному файлу
   пользователя). Не выдумывать схему: если образца нет — спросить владельца.
2. В модуль нужного самолёта добавить элемент в `outputs` (`id`, `format`, `dir`, `file`, `build`).
   Для новой внешней системы — по умолчанию `enabled = false`, пусть пользователь включит её в `config.lua`.
3. Данные брать из `situation` или переиспользовать `built["dcs-dtc"]`.
4. Если нужен формат, которого нет в `ENCODERS` (XML, INI…), добавить кодировщик в `SarmatDTC.lua`.
5. Покрыть тестом в `test_core.lua` (форма `content`, пути) и прогнать тесты.

### 3. Обновить классификацию юнитов/ПВО
- `AD_TYPES` (порядок = приоритет угрозы, первый совпавший побеждает) и `GROUND_CLASSES` в ядре.
- Новый ключ ПВО нужно сопоставить с символом во всех модулях, которые рисуют угрозы
  (`TGT_IDS` в `aircraft/AH-64D_BLK_II.lua`; без сопоставления используется общий символ) и добавить
  в `core.THREAT_DEFS` для F-16/F-18 (тест упадёт, если записи нет).
- Шаблоны — Lua patterns по строке `" " .. lower(type) .. " "`: экранировать `-` как `%-`,
  для номеров использовать `[^%d]` (`sa%-2[^%d]` не совпадёт с SA-20).
- Типы юнитов брать из `units.json` (`types[]`), названия ЗРК — из `status.json` (`strong[].name`).
- Сверять с подсказками сайта: `UNITSYM` в `map.html`.

### 4. Сайт изменил формат или адреса
- Скачать страницу (`map.html`, `assets/sarmat.js`) и найти `grab(`, `DATA =`, `BASE =`
  (данные лежат в `DATA + name` относительно страницы; Кавказ — с префиксом `/k`).
- Обновить `CONFIG.SITE`/`DATA_PATH` и разбор в `collect()`; обновить фикстуры одним запросом.

### 5. Отладка в игре
- Лог: `Saved Games\DCS.openbeta\Logs\dcs.log`, искать `SARMAT.DTC`.
- Кэш: `Scripts\SarmatDTC\cache\` (`done-<id>.flag` = `ok`/`fail`). Ручная проверка загрузки
  (флаг — `done-manual.flag`):
  `wscript //B //Nologo Scripts\SarmatDTC\fetch.vbs https://baikalprimestudio.com/data/`.
- После записи в чат приходит короткое локальное сообщение (`CONFIG.SHOW_CHAT`), например
  `SarmatDTC: BLUE DTC ready (Hatay): AH-64D, F-16C, FA-18C`: сторона, база спавна, записанные
  типы (часть до `_`). После ` - ` идут пометки: `download failed`/`download timed out`, `map data 2 h old`,
  `N error(s), see dcs.log`. Если записать нечего, сообщение имеет вид
  `SarmatDTC: download failed, map data too old (10 h), no DTC written`. Подробная статистика есть только в `dcs.log`.

## Порядок работы: сначала обсуждение, потом правки

- На новую задачу или вопрос сначала идёт обсуждение: разобраться в коде, предложить решение
  (что и в каких файлах меняется, какие есть варианты и риски) и ответить на вопросы владельца.
  На этом этапе файлы не правятся и команды с побочными эффектами не запускаются.
- Правки вносятся только по отдельной явной команде владельца («делай», «вноси», «правь»).
  Согласие с идеей в ходе обсуждения — ещё не команда.
- Одна команда покрывает только обсуждённый объём. Если по ходу работы нужно что-то сверх него,
  нужно остановиться и снова обсудить.
- Если сам запрос уже прямо требует конкретной правки («добавь X в Y»), это и есть команда.
